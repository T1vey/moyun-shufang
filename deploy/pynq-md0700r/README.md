# Verified PYNQ MD0700R display and GT911 touch

Board-tested on 2026-10-10 with PYNQ 2.7, Zynq-7020 and the 1024x600 MD0700R panel. The standalone GT911 fix passed repeated presses and sliding. The integrated GUI passed three distinct target clicks with press/release events; backend/display/touch service stop-start also passed. The new touch revision has not yet had a full physical power-cycle acceptance test.

Active bitstream SHA256: `dfc12ba5cc20d1c113fa5a6f80f00d5cf009c324888c72654b6781d7323f179e`. Matching exports: `dist/md0700r_touch_hardware_20261010`. Hardware source and rebuild instructions: `hw/md0700r/gt911_pl`.

The historical target deployment let the backend load the overlay. The new sealed platform deployment uses `so101-platform.service` to load it once and makes the backend attach. `md0700r_display.py` uses the existing Frame Buffer Read + VTC + PWM chain with a PYNQ contiguous 24-bit buffer and the user/settings GUIs on Xvfb :9. `gt911_input.py` reads the PL packet register at 0x41220008 and generates local X11 pointer events. Required packages/libraries: xvfb, python3-pil.imagetk, libX11, libXtst. No replacement kernel, touchscreen kernel module or display DTBO is required.

Installed helpers: `/usr/local/lib/so101-md0700r`. Services: `so101-workbench.service`, `so101-md0700r.service`, `so101-gt911.service`, all enabled. Display follows backend; input follows display through After/BindsTo/PartOf, with Wants dependencies starting the full chain. Stop backend before replacing/reloading hardware; this stops input and display first. Start backend to bring the chain back.

Display initialization: return shared LCD ID pins to RGB output after reading ID=2; VTC control 0x03f7ef07; Framebuffer format register 29 (BGR8), stride 3072. The complete installed FPGA-to-panel path requires RGB byte order in DMA memory: convert Xvfb little-endian B,G,R,X pixels with `panel_pixels()` before copying. Direct B,G,R copies swap red/blue on the physical panel. On 2026-10-11 the user confirmed the correction restored amber artwork, brown background and red seals. A normal Xvfb screenshot does not verify the downstream LCD color mapping. Touch fixes: select GT911 at address 0x14, read coordinates before ready-clear, wait for I2C STOP completion before the next command, and use explicit IOBUF pads through BD out-of-context synthesis. The initial fused touch build lost its input/tri-state pad buffers; routed-netlist checks now reject that condition.

Startup robustness: explicitly hold the display reset low for 100 ms, release and wait 100 ms; require two completed hardware frames through the frame buffer ISR before enabling backlight. CPU interrupts remain disabled. On shutdown, cancel auto-restart and wait for idle before reset/freeing the DMA buffer. This was added after a black-screen report that recovered after a display service restart; the original transient cause was not conclusively established. AP_CTRL 0x81 alone is normal during auto-restart and is not a stalled-stream indication.

The historical target migration updated the bit/HWH/register map together with `drawing_target.artifacts.json`, runtime PACKAGE_MANIFEST hashes and the then-hardcoded display/input expected hashes. Runtime health was checked against the matching hash. The 85-case IK gate passed; calibration was unchanged. Rollback backups are in `/home/xilinx/so101_deploy_md0700r_20261010/backup`.

For the planner release, use the installer in `scripts/install_planner_runtime.py`; the LightDM installer is for the older kernel-DRM architecture. The manifest declares `display_backend=pynq-mmio`, `touch_backend=gt911-pl-gpio`, no DTBO, and the exact HWH display/touch register contract. Both helpers take `--platform-manifest`, verify the boot receipt, and derive the bit hash from the sealed package. There is no per-release hardcoded planner bit hash. Workbench health must identify the same ABI, all three artifact hashes, a non-faulted backend, and `pl_load_policy=attach` before the display starts.

Startup ordering is platform loader -> backend attach -> display -> touch. The four `*-start` wrappers use `/etc/so101/desktop.env`: `SO101_APP`, `SO101_PLATFORM`, `SO101_DATA`, `SO101_PROFILE`, `SO101_PYTHON`, optional `SO101_PORT` (8765), `SO101_GUI_USER` (xilinx), and `SO101_ALLOW_MOTION` (0). Installer-selected data and port are forwarded to both backend and GUI. `SO101_ALLOW_MOTION=1` enables motion capability but does not initiate motion.

The planner backend explicitly obtains PS DDR from its sealed HWH in every attach process, avoiding PYNQ 2.7's process-local default-memory state. Display shutdown clears auto-restart and waits for actual frame-buffer idle before reset or release. A stuck or unreadable DMA retains its buffer and waits for maintenance; platform, backend and display services must not have a forced-kill stop timeout. Before replacing hardware, stop touch/display/backend, verify they exited, and remove only their stale runtime status files. The platform loader rejects a live backend or any remaining display/touch status file. A ready receipt proves platform identity and accelerator self-test; display frames and physical touch are accepted separately.

Status: `/run/so101-lcd/status.json` and `/run/so101-lcd/touch.json`. Temporary `touch_check.py` is a three-target acceptance screen and is not a startup service. No BOOT.BIN, kernel, modules or calibration files were changed, and no motor movement was commanded by the deployment checks.
