## 一批 IK 如何保持原规划语义

1. PS 保留原目标顺序，只有每个目标的第一次普通求解可以加入批次；恢复与重试沿用原流程。
2. 输入包含当前种子、静态求解参数、目标 ID、job ID、generation 与 context ID。新核最多连续求解 64 个目标，后一目标使用前一目标的结果。
3. PS 收到完整硬件完成信号后验证回执身份、长度、前缀、逐行状态、迭代预算和数据有效性，再逐目标消费。
4. 每个实际消费的 IK 解仍以独立 PS FP64 标量 FK 检查残差。硬件残差不能自行授权运动。
5. 原 PS 零迭代缓存仍为准。仅当投机首行完全匹配、状态成功、迭代数为 0、关节种子逐值相同时，消费首行并保留尾部；其余情况清除尾部。
6. 连续性拒绝、恢复、参数或种子变化会使尾部失效。算法迭代预算仍按原规划器统计，另将实际投机工作限制在每计划总迭代预算的两倍以内。

首次板测还暴露了 PS 重复准备批次的开销：虽然后端仍持有可消费的结果，原调度却在每个目标前再次复制后续最多 64 个目标。第二轮新增 `needs_target_batch()` 调度提示，仅在待提交输入和预取结果都为空时准备新批次；`prepare_calls`、`prepare_s` 纳入统计。种子、身份、预算和独立 FK 检查保持原有语义。调度修复后重新完成离线差分与下述板端六次测量。

这是减少 PS/PL 往返的实现，不代表目标间 IK 依赖被并行展开。当前采用单缓冲批处理；未宣称已经实现双缓冲重叠或完整 C++ PlanSession。

## DDR 协议与退出条件

ABI 为 `so101-planner-accel-v2`，HLS top 为 `planner_accel_v2`。DDR 记录均为小端，分配 64 字节对齐连续缓冲。实际 HLS 生成的寄存器映射由 `scripts/export_planner_register_map.py` 提取，不能从 DDR 结构偏移推测控制寄存器地址。

| 缓冲/记录 | 大小或上限 |
|---|---:|
| 固定 context | 512 字节 |
| IK 输入 / 输出行 | 32 / 64 字节；每批 1～64 行 |
| FK 输入 / 输出行 | 64 / 32 字节；每批 1～1024 行 |
| 完成回执 / 取消缓冲 | 各 64 字节 |
| 驱动固定缓冲总量 | 98,944 字节，不含分配器元数据 |

启动前先确认 IP idle，再填充缓冲并 flush；启动后不得改写输入。观察 `ap_done` 且 idle 后才 invalidate 输出并验证回执。取消字同时绑定 job 和 generation；IK 每目标、FK 每 64 行检查一次。超时主动请求取消，使会话失效并保留在途缓冲，禁止直接释放或重载共享显示平台。维护释放也必须先观察到 idle，释放后的会话不可复用。

驱动的同一把锁覆盖启动准备、执行和关闭；物理 IP 租约防止多个实例/进程同时改寄存器，平台加载器在下载前也获取租约。每批启动前记录在途标记，正常完成后清除。故障时以强引用和非 daemon 维护线程保留缓冲，直到观察到 idle；正常解释器退出也必须等待排空。实际写入、等待、读取时间分别计量。

SIGKILL、`os._exit` 和内核故障不受 Python 生命周期保护；遗留在途标记会拒绝新的会话，需要复位整个平台并重启，不能靠删标记或重载一部分共享显示逻辑恢复。已经创建 PYNQ 对象的进程禁止 fork。离线板端基准仍应先停止工作台服务，以获得明确的独占测试环境。

## FK_ROWS 当前用途

新核已能计算 FK 批次，但当前仅用于影子比对和启动自检。返回给正式几何判定的仍是 PS FP64 参考结果。样例最大误差小，不等于已经获得全关节域的保守误差上界，因此没有把 FP32 PL FK 直接替换整条轨迹的质量检查。

要继续推进正式 PL FK 加速，需要先给出适用关节域、工具参数、输入转换误差与运算误差的保守界；在阈值附近回退 PS，并证明原几何拒绝条件和全采样覆盖没有放宽。不能通过删点、降低检查密度或放宽误差阈值来宣称同等精度加速。

### 2026-10-11 板端规划时间

统计口径为板上完整轨迹生成与生产历史保存，不含图片向量化、HTTP、舵机预检及实体绘画。输入、初态及 `classic_fast` 配置固定。

| 人脸样例 | 旧 target 基线（各 1 次） | 新 planner 三次耗时 | 新版中位数 |
|---|---:|---|---:|
| 8 笔画 / 9,814 条命令 | 32.021 秒 | 27.733、24.328、24.024 秒 | 24.328 秒 |
| 32 笔画 / 8,356 条命令 | 26.375 秒 | 21.839、19.867、19.103 秒 | 19.867 秒 |

这两份样例当前完整规划约为 20～24 秒（中位数），相对各自单次旧基线约减少 24%～25%。旧基线只有一次，不能将这一比较解释为充分重复采样的统计结论，也不能把它外推为任意人脸图的保证时间或硬件理论极限。首次新版板测记录另存 `planner_face*_initial.json`；上表使用完成重复准备问题修复后的 `*_r2.json`。

另外，扩展后的生产基准 CLI 使用 `standard` 配置跑通三轮完整生成与历史保存。该配置的 8 笔画样例为 8,496 条命令；执行文件约 6.62 MB，历史引用约 0.277 MB，引用同一个 `plan.json`，不再复制完整轨迹。不同运动配置的命令数量不同，不能混用为性能加速比。

HLS R2 估算为 38,815 LUT、30,464 FF、99 DSP、19 BRAM18，较首版减少 2,519 LUT。随后 Vivado 新核独立综合得到 28,292 LUT、30,340 FF。最终融合显示、GT911 触摸与规划核的整机实现已成功生成 bit/HWH/XSA，实际结果如下；不能把前两种估算混作整机资源。

| 整机实现指标 | 旧平台 | 新平台 | 增量 |
|---|---:|---:|---:|
| LUT | 28,000 | 32,198 / 53,200 | +4,198 |
| FF | 34,835 | 37,929 / 106,400 | +3,094 |
| Slice | 10,824 | 11,874 / 13,300（89.28%） | +1,050 |
| BRAM36 等价块 | 6.5 | 15 / 140 | +8.5 |
| DSP | 100 | 100 / 220 | 0 |

新增资源符合方案的 6,000 LUT、30 DSP、16 BRAM36 预算。100 MHz 规划时钟下，最终 WNS=+0.148 ns、WHS=+0.040 ns，TNS/THS 均为 0；无未约束的内部端点、无缺失时钟。Slice 使用率接近九成，后续不宜直接再复制一套大计算核。

原平台的 4 个输入、33 个输出未设置 I/O delay 的情况仍保留，TIMING-4 / TIMING-27 两条 Critical Warning 也需按原平台约束背景和板端结果复核。本轮没有放宽约束以取得通过，不将“满足已设时序约束”写成所有外部 I/O 均已完成时序验收。

真实生成 HWH 已核对地址和位宽，兼容一个 64 位指针寄存器或两个精确相邻的 32 位寄存器；不允许缺高半字或混合两种表示。新旧生成的 `ps7_init.c/h/tcl` 完全相同，旧 XSA 中对应文件也一致；HP1 的 64 位配置与 FCLK0 100 MHz 原本已相同，没有发现新增 PS 初始化写入需求。后续在现有 PYNQ 启动环境中已完成真实 DDR 的 IK64/FK1024 核验和六次完整规划；HP1 通道可用性的证据来自这些实测，文件相同只是早期静态依据。

初轮软件测试、完整 C/RTL 联合仿真及融合实现状态见原报告目录 `implementation_status.json`。这些桌面证据与后续板上验收应分开引用；当前板端状态以 [板端部署记录](PLANNER_BOARD_DEPLOYMENT_20261011.md) 为准。

## 复现与选用

板载 PS 的原生库可使用目标环境的编译器构建：

```sh
python3 native/build.py --cxx g++
python3 -m unittest discover -s tests -p test_native_geometry.py -v
python3 -m unittest discover -s tests -p test_planner_accel_lifetime.py -v
```

构建参数关闭 fast-math、重结合与 FP contraction。部署库时必须连同 `.so.json` 构建清单和匹配源码；可以用 `SO101_NATIVE_GEOMETRY=off` 强制原实现作差分。早期交叉构建候选保留在 `build/planner_accel_arm/`；当前部署使用新发布目录内由板上编译器构建的库，未覆盖旧发布目录。

Windows 上重新构建新 HLS 核（使用全新的输出目录）：

```powershell
powershell -File hls_source/build_planner_accel_v2.ps1 -BuildDirectory C:/fpga_build/so101_planner_new_build
```

该脚本依次执行 csim、综合、cosim 与 IP 打包。随后使用 `hw/md0700r/create_fused.tcl` 的第四个参数 `planner` 创建融合工程，应用 `gt911_pl/apply_gt911_pl.tcl`，再运行 `build_fused.tcl`。当前打包选择 `--display-backend pynq-mmio`，使用真实导出的 mode 标记、bit、HWH、寄存器表和用户态显示/触摸接口契约，不添加 DTBO。只有另行选择 `kernel-drm` 路径才需要匹配内核的 DTBO。不要用旧 target 平台文件凑齐新文件名。

新运行配置示例为 `config/runtime.planner.example.json`，显式设置 `pl_mode=planner` 与 `pl_load_policy=attach`；现有默认 target 配置保留。只有匹配平台已在启动时加载并自检通过，工作台才可 attach；每次规划不重新下载 PL。

完整性能基准已增加 `--pl-mode planner`，当前板测已按固定输入、固定 q0 和相同配置完成。复测可在独占板端加速器的环境中执行以下命令；`NEW_OUTPUT` 必须是新目录：

```sh
python3 scripts/benchmark_planning_speed.py \
  --paths INPUT/paths.json --machine INPUT/machine.json --q0 INPUT/q0.json \
  --pl-mode planner --overlay overlay/planner_platform/drawing_planner.bit \
  --pl-load-policy attach --platform-manifest overlay/planner_platform/platform.json \
  --motion-mode classic_fast --runs 3 --output NEW_OUTPUT
```

基准不发送运动命令，统计完整 build 与生产历史保存，排除 HTTP 和舵机预检；记录每阶段时间、实际后端、核启动数、原生库状态和进程峰值内存。旧/new 硬件需要各自匹配整机平台、分别启动测量；必须保持输入、初态、约束和输出数一致。

开发电脑上的 `--native-library ... --pl-mode planner` 只验证软件链路。即使离线运行低于一秒，也不能将其写成 Zynq-7020 的规划时间。当前可引用的板端秒数为上表，详细分阶段时间见 `planner_face*_r2.json`。理论极限仍不能由核调用次数或桌面时间直接推出。
