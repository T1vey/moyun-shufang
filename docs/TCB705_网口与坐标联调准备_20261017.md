# 天链 TCB705 网口、TCP 与七轴联调准备

2026-10-17。用户已确认：天链机械臂与华成控制器尚未到手；将通过网线连接 ZYNQ。本次完成可离线开发的适配与验证，不能宣称已经完成真实机械臂联调。

## 连接方式

```text
手机 / 云端 ← Wi-Fi ESP8200 → ZYNQ7020
                              │
                         有线网口 eth0
                              │ 网线（或普通交换机）
                         华成控制器网口
                              │ 控制器内部运动总线
                         天链 TCB705 七轴
```

ZYNQ 上运行 GUI、图像处理、七轴 IK 和轨迹时间规划；网口通过厂商 SDK 给华成控制器提交七轴关节目标，控制器再连接机械臂。SDK 的 `init_data(localIp, remoteIp, port)` 同时需要 ZYNQ 的本地地址和控制器地址；有线端口不沿用旧 STS 舵机串口协议。

设置页增加了“板子有线 IP”和“SDK 端口”，保留“控制器 IP”和“Web 端口”。地址留空，避免把 ArmVision 历史地址当成到货设备地址。SDK 8001、Web 8010 是当前工程的参考端口，到货后需与控制器一致。

保存这些字段只保存应用连接参数，不改 Linux 网卡。到货后读取控制器实际地址，再为 ZYNQ 配置同一网段且不冲突的静态地址；Wi-Fi 保留默认路由，有线链路通常不另设默认网关。目前电脑部署使用 192.168.2.99，没有提前改成历史 192.168.4.x。

## TCP、基座与七轴映射怎样核对

现有参数分为三个独立部分：

1. `sdk_mapping`：SDK 七轴角度与 URDF 关节顺序、正负方向、零位偏置的对应。
2. `T_controller_base_from_model`：模型基座到控制器基座的刚体变换，默认单位阵。
3. `T_flange_tcp`：法兰到真实笔尖的变换。此前 80 mm 是占位示例，不能称为实测笔长。

计算链为 `T_controller_tcp = T_controller_base_from_model × FK_URDF(q_model) × T_flange_tcp`。

只读采集先等待至少两次配置反馈刷新周期，检查静止状态，读取前后两组关节；变化超过 0.02°、工具或工作坐标发生切换时拒绝样本。这个检查不能证明控制器缓存绝对新鲜，记录中仍明确标注没有控制器时间戳。

至少保存 10 个不同静止姿态；拟合组、独立核对组的每个轴都要有足够变化。工具用前半样本估计恒定基座变换，后半样本独立检查，避免把一个姿态碰巧对上当成整个模型正确。需要核对当前轴序/符号/零位候选；不会凭少量样本自动猜一个七轴排列并投入运动。

首轴零位与基座旋转、末轴零位与工具旋转可能相互补偿，仅靠末端数据不能保证唯一辨识。这也是报告只称“候选与 SDK FK 一致”的原因。需要结合厂商轴定义和已知基座参考，而不是把一个拟合成功的结果称为七轴本体自动标定。

SDK 的无工具 FK 与有工具 FK 都使用同一组关节角，可推算当前控制器定义的工具变换。工具编号 0 一般只是法兰，不能据此得到实际笔尖。原 A/B 纸面与 Z/UVW 标定保留，不等于已完成真实 TCP 标定。

真正测量笔尖时，可用固定笔尖、改变法兰方向的定点法。工具求解 `R_i × t_tcp + p_i = p_pivot`，检查矩阵秩、条件数、残差和留一检验。它只确定 TCP 平移，不确定笔杆方向；笔轴方向仍需安装几何或独立姿态测量确认。

全部报告只输出候选与误差，不覆盖配置、不自动写入 `*_verified=true`。拟合阈值是软件检查阈值，不是实体绘画精度承诺。SDK 位姿的 XYZ/UVW 单位及欧拉角约定必须确认后显式选择，不能从六个数字自动推断。

## 轨迹下发已做和仍需实测的边界

已写出的提交循环在任何发送前检查全部七轴目标的有限值、限位、时间顺序、周期、速度和起点偏差；按绝对时刻等待。迟到、SDK 调用耗时超过周期、返回失败或异常时退出，不追赶补发，不重试状态不明确的目标。停止接口返回成功只记录“停止请求已接受”。

最后一个点返回成功后状态为 `SUBMITTED_AWAITING_FEEDBACK`，`physical_completion_confirmed=false`。当前没有把这一状态变成“绘画完成”。也没有自动使能、清报警、切换运行模式或关闭控制器保护。

SDK 手册 V2.4.1 的有关证据：

- 第 21～23 页：`PluseToServo` 以度为单位；透传示例周期 2～4 ms；保护切换后等待至少 3 s。
- 第 23～24 页：关节/世界反馈默认刷新为 40/50 ms；因此不把每个发送周期的一次重复读数当作新反馈。
- 第 33～34 页：显式正解和坐标变换接口，tool/workspace=0 的 FK 用于基座法兰比对。
- 配套 `robot.h` 的 `clearRobotRoute` 说明针对路径清除与运动状态；对实时透传的实际停止效果仍需验证。

实际库还需一个经现场验证的监督层：进入/退出透传流程、保护恢复、开始时反馈对齐、控制器缓存与数据新鲜度、最终到位与停稳确认、异常停机确认。SDK 内部调用若一直阻塞，C++ 提交循环不能靠调用返回后的计时提供硬实时保护，需要确认控制器自身或独立看门狗的断流行为。

## 到货后的执行顺序

1. 核对控制器型号、Host 版本、SDK 版本、robotId、七轴配置与 IP。使用本工具只读连接。
2. 保留原始控制器配置，采集静止关节/法兰/工具样本，确认 SDK 位姿约定；核对轴序、符号、偏置与基座变换。
3. 核对实际笔尖 TCP 和笔杆方向，重新读取 A/B 与落笔 Z/UVW；避免沿用另一套安装的坐标。
4. 测实际透传周期、SDK 单次调用时间、反馈更新时间、丢包/断网/进程退出后的行为；确认停止请求与保护恢复的效果。
5. 补齐监督状态机和现场证据后，先做空载小范围测试，再验证固定姿态的竖直抬落笔、方框、圆和人像。

前 3 步可保持软件只读；改变姿态由现场明确控制。第 4～5 步涉及运动，需要设备在场和明确的测试范围。本次设备未到货，没有进行这些实机操作。

## 命令行示例

在项目根目录运行，先使用项目兼容的 Python 环境。板端备用目录目前可使用 `/home/xilinx/ZYNQArm/.venv/bin/python` 替代下例的 `python`。`machine.json` 为填写真实地址后的配置文件。命令输出文件均要求是新文件，避免覆盖原始证据。

```sh
python scripts/tcb705_commission.py network --profile machine.json --output network-check.json
python scripts/tcb705_commission.py capture --profile machine.json --output pose-01.json
python scripts/tcb705_commission.py audit --profile machine.json --input samples.json --pose-convention xyz_mm_uvw_deg_zyx --output coordinate-audit.json
python scripts/tcb705_commission.py pivot --input flange-transforms.json --output tcp-pivot.json
```

`samples.json` 是多个采集结果组成的 JSON 数组，采集时配置摘要须与被核对的配置一致。`flange-transforms.json` 是经过约定确认、以米为平移单位的多个 4×4 法兰变换矩阵；定点样本必须来自真实保持笔尖同一点的采集，不能拿任意姿态代替。
