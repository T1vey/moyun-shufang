一、修正先前结论

不能把“SDK V2.4.1 与控制器 1.9.71 低于文档配套门槛”直接等同于
“所有运动接口都不可用”。版本兼容问题确实存在，但仍未证实是完全不动的根因。
也不能要求先升级固件才能继续所有诊断；旧接口仍有可验证的功能。

本轮实际结果：
- 七轴反馈、世界坐标、指令坐标、七轴速度反馈均能读取。
- tryWorlds 能计算当前位姿与当前位姿上方 0.5 mm 的七轴解，越界掩码均为 0。
- 原试验的四个目标端点均能通过 tryWorlds 求解，越界掩码为 0。
- 同一进程内 inverseKinematics 对当前位姿返回 false，结果为空。
- 这证明部分旧功能可用、新运动学接口未正常工作；并不证明所有接口兼容。
- 四个端点可解不等于整条直线路径连续可达，不是碰撞检查或纸面高度验证。
- 全程机械臂反馈未发生动作变化，总使能和单臂使能均保持 0。

三、既有 SDK 测试中的问题与证据级别

1. 控制模式概念用错，已确认。
   line50_test.cpp 将 setHostCommunicationMode(1) 解释为“选择以太网控制”。
   V2.3.11 第 5-6 页和 robot.h 明确：这是控制器与示教器的通信方式。
   它不证明进入自动模式、取得外部运动权限或满足无示教器运行条件。
   原 GUI 的自动程序启动和本次 SDK 单点流程不同，应分别核对前置状态。
   不能简单给 SDK 单点流程补一个“程序运行键”，否则可能启动已有整幅绘画程序。

2. 使能顺序不一致，已确认；是否导致不动尚未证明。
   手册第 7 页示例先总使能，再单臂使能；既有试验先单臂，再补总使能。
   后续正式验证应遵循对应固件的厂家示例顺序，并分别等待有效状态。
   第二次旧试验已观察到两项使能都为 1 仍不运动，因此不能宣称调整顺序必然修好。

3. 速度倍率覆盖，已确认；不是完全不动的已证根因。
   maxLineSpeed=0.005 表示 5 mm/s，单位没有写错。
   specifyGlobalSpeed=1.0 表示 100%，覆盖当时读取到的全局 10%。
   后续测试应保留现场倍率或显式使用经过核算的低倍率，不应无意覆盖。
   不能在未实测插补语义时声称实际速度一定等于两个参数的简单乘积。

4. 请求返回成功不等于运动成功，已确认。
   needBlock=false、needCallback=false 时，当前库在请求成功后即可返回 0。
   既有程序后来通过反馈和 4 秒无进展检查判定失败，这个停止判据应保留。
   不动的定位应同时观察：请求响应、规划指令坐标、实际反馈、运动状态。
   仅把 needBlock 改成 true 不会自动修复控制器状态，还可能造成长时间等待。

5. 首次运动验证跨度过大，调试方法应改进。
   原测试第一段是从 Z≈292.373 到 Z=214.310，约 78.063 mm 的下降。
   它同时引入纸面、TCP、全程可达性和控制状态等变量。
   后续正式实机验证应先在当前附近做一个受限的空中微小位移，成功后才验证
   空中 50 mm 路径及落笔绘制。不能把试算成功当成允许直接下降的依据。

四、没有发现错误的部分

- 机器人 ID=1 的读取能取得七轴数据；不是把六轴向量硬塞给七轴接口。
- endWorld 为六维 XYZUVW，这是末端位姿格式，七轴机械臂也使用六维末端位姿。
- 直线目标的长度单位和 maxLineSpeed 的 m/s 换算无明显错误。
- 板上实际编译的 RobotActionParam 内存布局与 ARM32 库读取位置逐项吻合：
  endWorld=12，interrupt=48，needCallback=49，needBlock=50，delay=52，
  accTime=56，decTime=60，maxLineSpeed=64，specifyGlobalSpeed=72，
  collabRobotID=76，collabDirectionMask=80，smooth=84，endJointIndex=88。
  sizeof=96。未发现旧头文件/新库导致该参数结构错位的证据。
- 原 DLL 的 moveWorlds2 和当前 ARM32 的 moveLine 都构造 /robot/line 请求，
  基础字段均有 robot_id、pos、interpolation_en、worldCb、accTime、decTime、
  maxLineSpeed、specifyGlobalSpeed。新版另外支持更多字段。
  共享请求路径只说明不是完全不同的基础协议，不能证明旧控制器接受全部新字段。
- 两个库都将未指定协同 ID 的内部默认值转换为当前机器人 ID；
  这一点并不是仅在新版出现的异常，不能凭该字段推断误启动双臂协同。

六、后续应如何定位，避免再盲目换版本或换接口

首先取得曾经成功运动的原厂软件/ArmVision 对照记录：所用入口、控制模式、
示教器连接状态、总使能与单臂使能、驱动就绪。用户已确认实物曾成功运动，
但不能因此把当前驱动状态视为必然正常。

SDK 正式验证需要区分以下三种证据：
A. 请求成功，但控制器规划指令坐标没有变化：重点查运动操作模式、控制权限、
   请求字段和控制器侧错误记录；不能先归咎电机反馈。
B. 规划指令坐标变化，实际反馈不变：重点查实际驱动就绪、总线、抱闸和联锁。
C. 指令与反馈都变化：控制链路成立，再验证几何精度和 50 mm 路径。

当前只读数据中指令与反馈重合、速度为 0，是未发新动作时的正常静止现象，
不能用它倒推之前运动命令被拒绝在哪一级。旧测试未同时保存这两类位置。

HMI 未脱离和 EtherCAT OP 查询失败应作为待核查项；失败返回不等于总线非 OP。
不自动执行 detachHMI，不关闭保护，不清空报警，不用启动旧程序来试探控制状态。
也不混用 V2.3.11 头文件与 V2.4.1 库，不把 V2.5.2 天链 SDK 当作同一控制器接口：
其包内列出的控制器版本为 rtl114-24.03.42，协议端口和当前华成栈不同。

2. SDK 实际加载与连接已经核对

3. 使能标志不能替代真实驱动就绪确认
   静态核查中，setSingleRobotEnable 和 getSingleRobotEnableStatus 使用相同
   控制变量枚举 336；setter 成功、getter 为 true 不能独立证明各轴驱动进入 OP。
   robotEnableOrNot 的成功路径返回输入使能值，没有逐轴等待真实驱动就绪。
   总使能 getter 读枚举 522，setter 还写其他控制变量；不能将所有 getter
   简单概括成同一个变量回读。
   servoIsOpOrNot 查询失败时不更新输出参数：false + 初始化为 false 的输出
   应记录为“未知”，不能写成“EtherCAT 确认非 OP”。

4. 只读驱动状态查询结果
   对七轴分别提交 0x6041:00 / SDO_UINT16 读取，请求均返回接受，但没有回调。
   随后独立诊断取消应用层轴号/索引过滤，等待 10 秒，仍无回调。
   再用独立进程被动注册 /sdo/update 原始 topic，提交单轴同一只读查询，
   等待 10 秒，原始事件数仍为 0。未对生产进程注册或替换回调。
   当前不能读取有效 statusword，不能据此判断驱动故障或把零当作读取值。

   SDK 静态结构：readSdo 通过 /servo/sget 提交请求；/sdo/update 通过 SDK
   主动发起的 GetStreamRaw gRPC 流接收；本地 8001 HTTP 上传监听并不承担
   这条状态回调。SDK 内部还要解析 data 并匹配 pending map 才调用 SDO 回调。
   原始 topic 观察本次没有事件，仍不能区分控制器未发布、流式订阅未送达、
   版本/事件兼容性问题或驱动侧无结果。原 ArmVision V2.3.1 已有 readSdo，
   不能声称旧控制器必然不支持此接口。
