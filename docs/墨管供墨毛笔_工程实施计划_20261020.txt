ZYNQArm 墨管供墨毛笔书法工程实施计划
日期：2026-10-20
性质：基于本地代码与用户方案的实施规划；尚未修改运行程序、部署或执行机械臂运动。

一、结论与已确定条件

可以在当前 ZYNQArm 基础上接入毛笔书法，无须重写整个机械臂项目。
保留原来的图片绘画流程，增加独立的“毛笔书法”任务入口；两者共享七轴模型、IK、PL 加速、机械臂通信和界面框架。
第一版采用固定笔轴姿态、按标准笔顺写字、逐点提按、连续变速。复杂侧锋、转笔、强化学习和闭环视觉修正不放进首版。

用户已经明确：
1. 毛笔通过墨管供墨，不需要机械臂蘸墨。
2. 笔毛长度 9 mm。
3. 笔毛最宽处直径 2 mm。

这两个尺寸描述笔毛外形，不等于 TCP、允许下压量或实际落纸线宽。
不能据此认定“下压 6 mm 安全”，也不能把实际线宽固定为 2 mm。
原方案中的墨碗标定、蘸墨、擦笔动作全部取消。
供墨是重力、泵还是其他方式，目前未确定；暂不假设存在可由软件控制的阀或泵。
后续取得毛笔完整安装尺寸、供墨方式及实测标定后，再确定工具模型和接触参数。

二、分析依据与三个开源项目的取舍

输入资料：
• 桌面《机械臂毛笔书法_具体实现方案_20261020.docx》。
• 本工程 tcb705、user_gui、stroke_paths.py、native/tcb_planner、native/huacheng_bridge。
• maobi/chinese_caligraphy_robot。
• maobi/CalliRewrite。
• maobi/Robot_Arm_Write_Chinese。

1. chinese_caligraphy_robot
采用思路：汉字矢量轮廓、标准笔顺中线、距离场估计笔画宽度、平滑轨迹。
重新实现相关处理：该项目的栅格构造和坐标转换面向其自己的机械臂，不能原样移植。
其半径到 Z 的经验换算不适用于当前 9 mm × 2 mm 毛笔。
不能直接照搬其随意移动中线点的修正方法。

2. CalliRewrite
采用思路：通过实验建立毛笔参数模型、分析笔触宽度随动作的变化。
不在 ZYNQ 上安装完整强化学习训练链，不下载此前排除的训练数据、权重或演示素材。
其中归一化的半径和工具参数不能直接当作毫米。

3. Robot_Arm_Write_Chinese
采用思路：汉字笔顺组织与多字排版。
不采用其 uArm 驱动和逐点 wait/sleep 执行流程；该流程会造成当前项目最希望避免的停顿。

使用任何上游代码、字库或衍生数据前，记录来源、版本及相应许可/署名要求。缺少明确许可证的部分优先参考算法后独立实现，不能把“公开仓库”视为无限制授权。

三、整体数据流

输入汉字
→ 查询按笔顺组织的每笔轮廓与中线
→ 确定最终毫米尺寸及排版
→ 计算每笔的目标宽度
→ 通过实测毛笔模型转换为下压量与速度
→ 生成带提按、速度和动作事件的语义轨迹
→ ZYNQ 进行七轴连续 IK、PL 批处理与轨迹检查
→ 生成可验证的执行节点
→ SDK 下发运动、逐段速度及必要停顿
→ 用户确认后执行。

汉字已有矢量数据时，直接进入矢量轨迹链，不经过云端线稿提取、骨架化或 outside_in 图像笔画排序。
因此文本书法可以避开图片线稿提取阶段的耗时，但完整规划耗时仍须测量 IK、合并检查和程序构建。
无字库条目的字首版明确提示不支持，不自动用图像骨架冒充标准笔顺。

四、新增模块及职责

建议新增 calligraphy/：

__init__.py
  对外入口，不包含机械臂驱动。

schema.py
  校验书法任务、单位、笔顺、工具配置、逐段速度与事件。
  明确区分节点属性、区间属性及到位后事件。

hanzi_data.py
  读取本地 graphics.txt，建立字符到文件字节偏移的索引。
  按需读取字形，不让每次查询都扫描或加载全部字库。
  保留每个字内部的标准笔顺和方向。

layout.py
  处理字格、字距、行距、边距和纸面范围。
  等比例缩放，不能横纵独立拉伸汉字。
  确定最终毫米尺寸后再计算目标线宽。

geometry.py
  将每一笔的 SVG 闭合轮廓正确填充为掩膜。
  在每一笔自己的掩膜上计算距离场，沿对应中线取宽度。
  检查中线是否落在轮廓内；异常字形给出明确诊断。
  对曲率、宽度变化大的位置自适应加密。

brush_model.py
  保存实际毛笔的线宽—下压量标定曲线及有效速度范围。
  配置记录毛长 9 mm、最大外形直径 2 mm。
  不生成虚构的已标定曲线，也不预设 6 mm 下压上限。
  根据可实现线宽范围压缩/映射字形宽度；不可实现时提示或拒绝。

stroke_rules.py
  处理起笔、行笔、转折、收笔。
  首版以轮廓宽度和少量经验证的动作模板为基础。
  不能仅凭笔画端点方向就强行添加回锋或大幅顿笔。
  “永”的复合笔画需要分段处理，不能视为一种单一方向。

task_builder.py
  生成统一毫米坐标下的书法任务，保留稳定的节点/事件标识。
  插入抬笔、移笔、落笔以及必要的局部停顿。
  无蘸墨动作。

preview.py
  按目标或标定后可实现的宽度生成可变粗细轮廓预览。
  沿用当前主界面的金色线条、深色背景风格。
  主用户界面只显示作品预测图，不叠加笔顺编号。
  预览属于几何预测，不宣称精确模拟墨水扩散和纸张吸墨。

五、任务数据结构

新增独立格式 tcb705-brush-path-v1，不把原 Nx2 路径直接改成 Nx4 并沿用旧校验。

任务至少包含：
• 字符串、字库版本、字形来源和排版参数。
• 纸面/工具/毛笔标定版本及摘要。
• strokes，按字符顺序和字符内部笔顺排列。
• 每笔稳定 ID、字符序号、原始笔画序号。
• xy_mm：节点纸面坐标。
• depth_mm：节点虚拟下压量。
• width_mm：节点目标线宽，用于预览和诊断。
• feed_mm_s：每个运动区间的规划速度上限。
• events：关联稳定节点 ID 的到位停顿等动作。

xy/depth/width 有 N 项，区间速度有 N-1 项，校验时严格检查。
同 XY、不同下压量的节点必须保留，不能作为重复点删除。
停顿事件即使没有空间位移，也不能被零长度路径过滤器丢掉。
插值加密后事件要重新映射；禁止继续使用过期数组下标。
任务摘要必须覆盖下压、速度、事件、字形版本与毛笔标定。

六、现有工程必须同步修改的文件

1. stroke_paths.py
保留老二维图像路径格式。
新增书法路径的独立验证/分发入口或调用 schema.py。
避免 resize_paths、validate_paths 和 path_digest 丢弃新字段。
书法任务不调用 outside_in。

2. tcb705/calibration.py
复用天链 A/B 点、落笔 Z 和工具姿态的标定入口。
为毛笔增加独立工具/纸面配置，不能覆盖后直接套用旧笔的 TCP 和落笔 Z。
首版按当前水平纸面模型工作；现有 A/B+Z 不等于完整倾斜平面标定。
若以后支持倾斜纸面，再增加非共线接触点和法向拟合。

3. tcb705/planner.py
新增书法规划分支，输入语义轨迹。
关闭该分支的最近邻笔顺重排和路径反转。
逐点计算接触位置，使用上一组关节解作为下一点的连续 IK 初值。
复用现有 PL 批处理、细分、关节约束和碰撞检查。
在细分、重定时、节点输出时保留速度、深度和事件。
当前重定时使用区段起点速度计算整段时长，必须改为尊重区间速度上限。
速度改变不应自动意味着完全停车；仅明确停顿/尖角等需要停止的位置强制到位。

4. tcb705/artifact.py
增加带书法属性的 plan/nodes 版本，并兼容旧 v1。
修改 nodes_of、freeze、check_frozen 及磁盘存取验证。
内存计划和保存计划都必须保留下压、速度和停顿。
更新预览输出，禁止新元数据通过“规划→执行”时丢失。

5. tcb705/web_executor.py
按语义节点构造下发程序。
合并节点必须保留深度极值、动作边界、供墨相关事件及重要速度变化点。
检查合并后的关节插值轨迹，不只检查原始 IK 节点。
除了位置偏差，还检查笔轴姿态偏差和纸面法向深度误差。
任务切块必须有明确策略：落笔段不允许因块数上限而无提示暂停。
控制器队列不能保证连续衔接时，应在规划前限制或调整任务，而非执行到一半才发现。

6. native/tcb_planner/core.cpp 及 Python 绑定
当前存在 C++ 节点合并和误差检查加速，不能只修改 Python 回退实现。
同步增加语义边界保留、姿态误差和法向深度检查。
变更接口时显式升级 ABI/能力版本；新 Python 检测到旧动态库时要拒绝错配或明确回退。
重新编译 ARM32 动态库，验证 Python 与 C++ 两条路径结果一致。

7. tcb705/sdk_motion.py
当前 start() 只留下运动类型、终点和 smooth，未传递程序块的 speed、delay。
新增逐段速度传递及独立的到位停顿事件。
pump() 需要识别事件屏障：前序运动完成后才能停顿，停顿结束后才能继续投递。
使用可取消的计时状态机，不在有后续运动已经排队时盲目 sleep。
idle/finish 也要包含事件完成状态，不能把等待停顿误判为全部结束。

8. native/huacheng_bridge/sdk_server.cpp
桥接已有 specifyGlobalSpeed 的 ratio 通道，优先复用。
SDK 头文件规定值为 0～1，0 表示使用当前全局速度。
任务中的 150% 相对速度不能直接传成 ratio=1.5；须结合基准比例转换并限幅。
文档将 delay_in_ms 说明为“延时下发”，不能据此当成“到位后驻留”。
到位驻留先采用明确完成反馈后的主机事件屏障。
实机验证逐条速度参数是否按预期生效，再确定最终队列深度和连续过渡策略。

9. tcb705/workbench.py、planning_session.py、user_gui/workflow.py
新增 calligraphy 任务类型，接通输入、规划、预览、确认、执行和取消。
复用热启动模型/PL 会话。
任意工具标定或毛笔曲线变化都使旧计划失效。

10. user_gui/display_server.py、user_gui/static、设置界面
新增书法文字输入、字大小与排版入口。
沿用当前 GUI 风格、准备完毕状态及确认执行流程。
调试页增加毛笔工具标定、线宽试写、供墨说明和执行日志。
不要在主界面暴露 IK/队列/ABI 等实现参数。

11. tcb705/config.py、collision.py、bridge.py 及相关验证
登记毛笔工具配置、有效下压范围、姿态容差、墨管限制与任务摘要。
检查所有计划 schema、阶段枚举和节点校验，避免新格式仅在一处接受。
刚性笔杆和柔性笔毛接触区分开建模。
仅允许明确落纸阶段、有效纸面范围内的笔毛接触；不能全局降低 CONTACT_HEIGHT。
墨管形状未知时，不宣称现有机器人碰撞模型能完整检测软管碰撞。

七、毛笔 TCP、提按与竖直抬笔

工具建模以安装好的笔尖为基准，包含法兰到笔夹、笔杆和自然伸展笔尖的变换。
9 mm 仅为笔毛长度，不能代替整个工具长度。
笔毛直径 2 mm 不能代替笔杆/接头碰撞半径。

接触段的几何定义：
P = O + u*x + v*y - n*d
其中 O 为纸面基准，u/v 为纸面方向，n 为向上的法向；
x、y、d 均在统一单位下参与计算。

d 表示自然笔尖相对纸面的“虚拟侵入量”，用于描述笔毛/夹具的变形。
这不是力传感闭环；没有力传感器时不能声称精确控制落笔压力。
如使用弹性夹具，实测曲线必须包含夹具变形的影响。

第一版纸面水平，笔轴相对纸面保持垂直。
抬笔时固定纸面 X/Y，逐渐减小 d 至脱离纸面，再升到移笔高度。
整个接触和抬笔过程使用七轴协同运动，不能沿用 SO101 的“只控制 ID3/ID4”规则。
需要检查整段插值姿态；节点处竖直并不保证节点之间也竖直。
实际竖直误差受工具标定、关节误差和控制器插补影响，用容差验收，不能承诺数学意义上的绝对零误差。

八、墨管供墨的专项处理

1. 取消蘸墨相关流程
不创建墨碗坐标、蘸墨深度、擦笔轨迹，也不按累计书写长度暂停去蘸墨。
不照搬原方案的 12 mm 蘸墨或每 250 mm 蘸墨。

2. 标定停笔积墨
毛笔持续供墨时，长时间顿笔可能形成墨团。
首先用无驻留的减速/提按表达顿笔；确实需要停顿再通过实测确定。
不能直接套用固定 0.3 秒驻留。
暂停、结束和故障状态都应考虑笔尖是否仍接触纸面。

3. 根据实际硬件决定供墨控制
若为无电控的重力/毛细供墨：软件只能通过动作、速度和操作流程管理墨迹，不能承诺停止供墨。
若有电控泵/阀：取得电气与控制接口后再增加独立 ink_supply 适配器，测试开关延迟和残余滴墨。
不得编造 SDK 中不存在的供墨函数或直接选择未核实的 IO。

4. 墨管布置与运动范围
固定软管并保留适量松弛，避免拉扯笔夹、卷入关节或限制腕部转动。
第一版固定工具朝向，优先选择关节连续、腕部扭转较小的解。
通过实际布管确定额外关节/姿态限制，不能只凭 URDF 判定软管安全。
供墨压力、液位变化、墨液和纸张改变时，线宽曲线可能需要复核。

5. 故障处理
原工程存在异常后自动 go_home 的路径，毛笔任务要单独梳理。
位姿可信且控制器允许时，才能按已验证路径受控脱离纸面。
反馈失效、失能或轨迹状态不明时，不盲目发归位运动。
有电控供墨时尝试关闭供墨并报告结果；无电控时明确提示人工处理。
保留原工程的取消、急停、故障记录，不能通过删除保护达到“连续书写”。

九、这支 9 mm × 2 mm 毛笔的标定与字形适配

首先确定自然笔尖接触纸面的零点，再以保守的小增量试写短线。
具体增量和最大下压值在观察笔毛形变、夹持方式和工具空间后确定，当前不写死。
分别测试不同下压量和少量速度档下的稳定线宽、墨团、断墨和回弹。
每组参数重复试写，拟合单调的线宽—下压量关系并保存有效范围。
线宽变化有迟滞时，需要限制深度变化速率，不能只做静态查表。

对于超出可实现线宽范围的原字形：
优先压缩粗细变化、等比例调整字大小，保留笔顺和结构；
不可通过无限加大下压去追求宽笔画。
2 mm 是笔毛外形最大直径，接触后铺开的宽度可能不同，必须实测。
首版先输出适合这支细笔的楷书效果，不承诺复现宽大铺毫笔触。

十、FPGA 与 CPU 的工作划分

ZYNQ ARM：
字库索引、SVG 轮廓解析、排版、宽度估计、毛笔模型、事件编排和 SDK 通信。
几何预处理优先采用现有编译库/向量化方式，避免逐像素 Python 循环。

PL：
复用工程已有的七轴 IK/轨迹批处理加速链。
只要调用契约与输入规模兼容，首版不需要为了“新增毛笔功能”修改 RTL 或重编 bitstream。
这不代表毛笔宽度分析已经硬件化。
如后续实际测量发现新的 PL 瓶颈，再单独立项修改硬件、建立/编译 Vivado 工程并验证产物匹配。

需要重新编译的内容：
变更后的 native/tcb_planner ARM32 动态库；
只有确需修改通信协议时才重编 SDK bridge；
Python 和 GUI 按项目现有部署流程发布。

十一、实施顺序与阶段验收

阶段 A：任务格式与数据贯通
完成 schema、字库索引、等比例排版、笔顺保留、模拟任务输出。
先修复/扩展 SDK 速度与事件传递，使用虚拟 SDK 校验，不驱动实物。
验收：永 5 笔、和 8 笔、九 2 笔、年 6 笔，方向不被反转。
检查字库负 Y 范围以及已有坐标系转换，避免重复翻转或镜像。

阶段 B：毛笔轨迹与完整计划链
接入深度、速度、停顿语义，更新 plan/nodes 格式和摘要。
同步 Python/C++ 合并与误差检查，保留关键提按动作。
验收：同 XY 不同 Z 能执行为独立动作；驻留事件不丢失；旧二维任务仍能规划。
改变毛笔曲线、TCP 或纸面配置后，旧计划必须失效。

阶段 C：离线与悬空验证
检查限位、碰撞、关节连续性、姿态和深度误差。
检查真实下发后的合并关节轨迹，而不只检查规划中的密集节点。
悬空确认字形、笔顺、提按方向、逐段变速和取消行为。
SDK 命令返回成功不等于已到位；完成反馈与实际位姿必须对应。
无真实反馈时只能完成模拟验收，不能标记实机通过。

阶段 D：细毛笔实测
完成 TCP、落纸零点、线宽曲线和供墨稳定性标定。
先写直线、弧线及粗细渐变，再写“永”。
同一参数连续写多次，检查粗细重复性、飞白/断墨、起收笔墨团及抬笔拖痕。
数值验收阈值依据实际毛笔与机械臂能力确定，不用任意精度承诺代替测量。

阶段 E：GUI 与多字验收
文字输入→预览→自动规划→准备完毕→用户确认→执行。
四字排版测试；任务间切换、取消、供墨异常提示和返回设置均验证。
最后才作为正式功能部署，保留可回滚版本。

十二、必须安排的有效测试

• 数据：字库索引、笔顺/方向、边界、等比缩放、缺字处理。
• 几何：每笔填充掩膜正确，中线宽度取样不跨到其他笔画。
• 轨迹：深度极值、零 XY 位移提按、驻留、速度变化在细分和合并后保留。
• 执行：假回调测试完成/拒绝/超时/取消，后续运动不能越过驻留屏障。
• SDK：确认 ratio 转换范围；区分延时下发与到位停顿。
• 兼容：旧图片任务输入、计划冻结和执行节点行为回归。
• 原生加速：Python 与 ARM32 C++ 关键结果一致，ABI 错配可检测。
• 实际插补：位置、笔轴角度、纸面法向深度及语义事件顺序检查。

十三、性能与交付口径

不能将本地 4 ms 规划采样等同于 SDK 每 4 ms 按同一轨迹执行。
当前执行器会合并关节节点，由控制器再次插补；计划时长不是未经校准的真实书写时长。
分别记录：字形加载、宽度处理、IK、约束检查、节点合并、程序构建、实际执行耗时。
同时记录点数、笔画数、下发块数、停顿时间和错误次数。
文档提出的“30～60 秒/字”“数秒规划”只作为待测试参考，不能当作已经达成。
