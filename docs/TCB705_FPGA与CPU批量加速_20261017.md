交付工程：`D:\zhiliao\TCB705_ZYNQ-10-15\ZYNQArm`。原 SO101 参考目录未修改。

复用 1013 的 PS/PL 分工、DDR 批处理、上一点种子延续、超时后 DMA 资源保留、物理 IP 独占锁和显示融合平台。模型与数据格式改为 TCB705 七轴，不能直接使用原五轴比特流。

| 部分 | 实现 |
|---|---|
| CPU 逆解调度 | 一次准备最多 64 个连续目标，前一点解作为后一点种子；路径细分或种子变化时丢弃未使用的批次后缀 |
| CPU 数值核心 | FP64 C++ 七轴 FK、Jacobian、IK；缓存模型和求解选项 |
| CPU 轨迹检验 | 最多 1024 行的 FK 批量调用；五次多项式极值改为原生 C++ 有界求根；保留原采样与动态限制 |
| FPGA 核 | `tcb_planner_accel`，独立 FCLK1 约 76.923 MHz，FP64，`IK_CHAIN` 上限 64，`FK_ROWS` 上限 1024 |
| AXI | 控制寄存器 `0x40000000 / 64 KiB`；64 位 M_AXI 经 PS HP1 访问 DDR；LCD 仍使用 HP0 |
| 算法分工 | FPGA 提供局部连续 IK 候选；CPU 独立 FK 验证每个候选并保留全局/大姿态逆解与最终轨迹检查 |
| 显示触摸 | 原 MD0700R 1024×600、GT911 PL 触摸桥；保留已修好的红蓝通道顺序 |
| 启动 | Linux 服务加载一次融合比特流，完成真实 IK/FK 自检后写启动凭据；业务程序仅附加，不重复下载 |

FPGA 按实际 URDF 的七个局部 ±Z 转轴实现，父变换、工具变换、限位、初值从 DDR 上下文传入。局部姿态误差使用小角度形式，较大姿态变化回到 CPU 完整求解器。CPU 验证仍使用配置中的原始位置和姿态容差；FPGA 不通过放松精度阈值获得速度。

生产规划的最终几何与碰撞检验仍在 CPU 上执行。FPGA 的 FK 批处理接口用于独立硬件验证，不能把它算作已替代全部 CPU 几何检查。

最终 R4 HLS 核已完成 C 仿真、综合、C/RTL 联合仿真与 IP 封装。RTL 检验包含真实七轴 IK、完整 FK、身份错误、取消和批次边界。HLS 估算为 30,895 LUT、25,380 FF、141 DSP、52 个 BRAM18；这些是核级估算，整机结果以 Vivado 布局布线后的报告为准。

FPGA 数学与 CPU 数学可能因运算顺序产生最后几位差异，离线小轨迹 SDK float32 输出在一 ULP 内，不承诺位级完全相同。最终必须同时通过独立 CPU FK、路径误差、姿态误差及动态限制检验。

首轮整机 100 MHz 实现的 setup 裕量约 −1.70 ns，失败路径为三角函数内部 22 级长逻辑，没有将该版本下载到板子。最终硬件为七轴核单独设置 IO PLL 来源的 FCLK1（约 76.923 MHz），GP0/触摸仍为 100 MHz、LCD 仍为 51.2 MHz，控制跨时钟由 Vivado AXI Clock Converter 处理。

2026-10-17 13:13 首个 76.923 MHz 实现虽然通过时序和 DRC，但在板端首次 MMIO 访问时失去响应。复查发现新建 `proc_sys_reset` 的默认辅助复位为低有效，而接线为常低，导致加速器一直复位。该失败版本已封存在 `build/fpga/failed_aux_reset/`，不能用于部署。修正版显式设置 `C_EXT_RESET_HIGH=0`、`C_AUX_RESET_HIGH=1`，重新综合、布局布线；新增 HWH 复位极性/接线检查和下载前 PS 复位寄存器检查。板子重新上电后已恢复原显示/触摸平台。

## 真实 FPGA 下载及性能结果

修正版已经通过 PYNQ FPGA Manager 实际下载到 ZYNQ7020，实际 FCLK1 读数 **76.923076 MHz**，AXI 控制寄存器空闲读数 **0x4**。独立 CPU 金标准验证了 **3 个 IK 目标和 1024 组七轴 FK**。FPGA Manager 状态为 `operating`，LCD 硬件出帧与 GT911 服务均正常。

原有显示 unit 的 `BindsTo/PartOf` 不能靠空的 drop-in 指令清除，曾使旧 SO101 后台被重新拉起，进而反复重启显示。部署现已替换这份基础 unit，只依赖天链后台和平台服务；原始 unit 有备份，回退脚本会恢复它。

应用采用 `PlanningSession` 常驻硬件会话：首次规划附加一次，后续规划复用；退出时先取消并排空 DMA，再释放会话。本轮一次性附加测得 **7.103 s**，不计入下表稳态规划时间；首个新会话仍需支付该开销。独立一次性 CLI 的 `plan()` 仍按调用开关会话。每次规划的 PL 次数按本次差量统计，不把历史次数当作本次工作。

同一块 ZYNQ、界面运行时、相同输入/采样/精度下的三轮中位数，无机械臂运动：

| 输入 | 新原生 CPU | 新 CPU＋PL | PL 批次 / CPU 验证接受行 | CPU 回退批次 |
|---|---:|---:|---:|---:|
| 两笔，187 节点、6345 帧 | 0.784 s | 1.052 s | 3 / 122 | 1 |
| 100×100 mm 人像前 8 笔，2467 节点、99465 帧 | 10.719 s | 15.716 s | 39 / 2402 | 1 |

**这版 FPGA 已参与真实七轴计算，但尚未比优化后的 ARM CPU 更快。可证实的大幅提速来自 CPU 批处理，不能把约 11～12 倍的历史提速称为 FPGA 加速比。** 默认应用保留用户要求的 CPU＋PL 路径。要争取 PL 额外收益，后续需减少 FP64 串行资源复用、增加核内并行并权衡 LUT/DSP/时序，不能仅提高时钟或减少校验。目前已完成源码移植、Vivado 实现、实际加载和真实计算验证；尚未达到 PL 超过优化 CPU 的性能目标。

每轮的一个 CPU 回退是 PL 局部求解器未满足原始容差，CPU 拒绝候选后以完整求解器继续。例如返回位置误差约 1.20 µm、姿态误差约 6.50 µrad，超过候选原始阈值，不能直接接受。三轮均无传输/协议异常。此前“大姿态变化导致首段回退”的推测没有得到数据支持，最终依据为上述实际误差记录。

数值验收以独立 CPU FK 检查最终 SDK float32 七轴目标；生产路径、姿态、碰撞和动态限制均未放宽。CPU/PL 七轴结果不是位级相同，要求每个关节差小于 3×10⁻⁷ rad 的附加比较没有通过。直接比较笔尖，两笔最大位置差 **0.000161 mm**，人像片段 **0.003970 mm**；人像同索引采样还包含约 **0.0833 ms** 重定时差异。额外 1 µm 直接比较在人像片段上未通过，报告保留 `direct_comparison_within_1um=false`。最终按原有 0.1 mm 路径要求验收，且每条轨迹自身通过独立检查；人像 PL 结果最大路径偏差约 **0.02167 mm**。以上是模型计算数值，不是实体绘画精度。

## 重建步骤

工具：Vitis/Vivado 2024.2；HLS 工作目录使用短英文路径。以新目录重建，避免覆盖现有可用版本：

```powershell
& .\scripts\build_tcb705_hls.ps1 -BuildDirectory C:\fpga_build\tcb705_next -Stage all
& .\scripts\build_tcb705_vivado.ps1 -HlsDirectory C:\fpga_build\tcb705_next -ProjectDirectory .\build\vivado_next -IpDirectory .\hw\ip\tcb7_next
```

只有综合、实现、setup/hold 时序和 DRC 检查通过后，构建才生成 `export/build_verified.json`。使用 `scripts/package_tcb705_platform.py` 从这个导出目录及该次 HLS 的 `xtcb_planner_accel_hw.h` 提取寄存器定义，生成全套平台封印。不能手改寄存器偏移，不能只替换 bit 文件。

板端顺序：上传并核对源码哈希 → ARM 原生编译和回归 → 检查平台封印 → 停止触摸、排空显示 DMA、停止规划服务 → 取得物理 IP 锁 → 下载融合比特流 → 真实七轴 IK/FK 自检 → 启动主界面与触摸 → 记录实际 PL 调用和性能。

本次采用 PYNQ 在 Linux 启动后加载 PL，并由 systemd 自动执行，保持 SD Card 启动；无需改写 BOOT.bin 或 FSBL。比特流本身在断电后丢失，但 SD 卡上的文件保留，下次启动会重新加载。

## 当前实机边界

TCB705 与华成控制器尚未到手。FPGA 编译、板端规划和屏幕运行都不能代替真实控制器验收。现有 A/B、落笔 Z/UVW 参数和 GUI 流程保留；TCP/基座/七轴映射、控制周期及 PluseToServo 真实下发仍需到货后核对。当前真实绘画入口继续明确拒绝未联调的机器人运动。

回退脚本只停止并排空 DMA 后恢复此前的完整平台，不清除 in-flight 标记，不强杀拥有 CMA 内存的规划进程。若硬件无法排空，应处理挂起原因或重新上电，不通过删除锁标记掩盖问题。
